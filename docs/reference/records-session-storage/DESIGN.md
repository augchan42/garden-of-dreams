# Account session storage candidate

The existing Garden identity addon needs encrypted Records access/refresh persistence before reading/history can work. This candidate extends its storage only. It stays separate from the active water-edge source and remains disconnected from plugin methods, UI and deployed services.

Keep one active verified Records owner in an AES-256-GCM authenticated envelope under Android no-backup storage with a separate Android Keystore alias. A persistent random owner epoch identifies the current authenticated session. It survives access-token refresh, so an authenticated request can retry after a 401 and publish its result against the same owner lease. Each credential replacement separately changes its random revision. A refresh can commit only against the exact predecessor revision and owner epoch; simultaneous refreshes cannot both commit. A new sign-in, including another sign-in for the same account, creates a new owner epoch. Sign-out persists an encrypted empty state with a new revision. Late sign-in, refresh and history responses cannot cross these boundaries. Corruption, malformed payloads and a missing key fail without replacing existing bytes or falling back to anonymous identity.

Use the current app_account_token, access-token expiration and optional paired refresh credential/expiration fields from inspected Records contracts. Expirations are Unix seconds, matching the server token mint and refresh response. Storage does not authenticate arbitrary caller-supplied credentials; eventual service exchange must establish ownership and use server verified responses. Expired access remains stored for legitimate refresh; an expired refresh remains an explicit error for the adapter, not an automatic downgrade. No real token is read, minted or transmitted during tests.

The same-process static storage lock serializes all store instances; AtomicFile alone does not provide locking. Storage and cryptography run off the main thread. Check and publication can share the storage lock, but a subsequently queued Godot or UI callback must check its owner lease again when delivered. A future client with multiple processes needs an operating-system lock.

V2 passes 22 JVM checks and 11 actual Android Keystore tests, including competing refresh writers, refresh with a stable owner lease and replacement sign-in for the same account. The existing three device-identity tests also pass against the same APK, whose installed bytes match the build. The first version's genuine passing results remain under verified-v1; it was rejected because it changed the owner lease during refresh, breaking the inspected request-retry contract. The envelope remains version 1 and its authenticated plaintext schema is version 2. No released-storage migration is claimed.

Keep the addon disabled. These storage classes remain disconnected from plugin methods, Godot controls and deployed services. Compilation and storage evidence does not establish Google sign-in, deployed session verification, account-history ownership, current-scene performance or release acceptance.
